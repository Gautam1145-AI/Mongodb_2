MONGODB REPLICATION - TERMINAL IMPLEMENTATION
================================================

Topics:
1. Purpose and setup of replication
2. Primary and Secondary roles
3. Read Preference
4. Write Concern
5. Elections and primary failure

Requirements
------------
- MongoDB Server (mongod)
- MongoDB Shell (mongosh)
- Three local MongoDB server processes
- This example is for local learning only. All three members run on one machine,
  so this is not production-grade high availability.
- Commands below assume macOS/Linux and that `mongod` and `mongosh` are in PATH.

IMPORTANT
---------
Keep each mongod server running in its own Terminal tab. Use a fourth tab for
mongosh commands. Do not run shell commands such as `mongod` inside mongosh.

------------------------------------------------------------
1. PURPOSE AND SETUP OF REPLICATION
------------------------------------------------------------

Replication keeps multiple copies of data across members of a replica set.
It improves availability, provides redundant copies, and can support reads from
secondary members. Replication is asynchronous, so secondaries can briefly lag.

A. Create data directories (run in normal Terminal):

mkdir -p ~/mongo-replica/data1 ~/mongo-replica/data2 ~/mongo-replica/data3

B. Start server 1 in Terminal 1:

mongod --replSet rs0 --port 27017 --dbpath ~/mongo-replica/data1 --bind_ip localhost

C. Start server 2 in Terminal 2:

mongod --replSet rs0 --port 27018 --dbpath ~/mongo-replica/data2 --bind_ip localhost

D. Start server 3 in Terminal 3:

mongod --replSet rs0 --port 27019 --dbpath ~/mongo-replica/data3 --bind_ip localhost

Leave all three server terminals running. If a port is already occupied, identify
the existing process and stop it safely before retrying.

E. Connect from Terminal 4:

mongosh --port 27017

F. Initialize the replica set once, inside mongosh:

rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "localhost:27017" },
    { _id: 1, host: "localhost:27018" },
    { _id: 2, host: "localhost:27019" }
  ]
})

Wait a few seconds, then verify:

rs.status().members.map(m => ({
  name: m.name,
  state: m.stateStr
}))

Expected: one PRIMARY and two SECONDARY members. The member elected PRIMARY
may vary. Do not run rs.initiate() again if the set is already initialized.

------------------------------------------------------------
2. PRIMARY AND SECONDARY: ROLES AND PURPOSES
------------------------------------------------------------

- PRIMARY: normally accepts writes and records changes in the oplog.
- SECONDARY: replicates changes from the primary and can serve reads when the
  client's read preference permits it.
- Election: eligible voting members can elect a new primary if the current
  primary becomes unavailable, provided a voting majority is available.

A. In the primary mongosh connection, select a database and insert a document:

use collegeDB

db.replicationDemo.insertOne(
  { student: "Aman", branch: "CSE", marks: 90 },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
)

B. Read from the primary:

db.replicationDemo.find()

C. Open another Terminal and connect directly to a secondary (port 27018):

mongosh "mongodb://localhost:27018/?directConnection=true"

Inside that shell, explicitly allow secondary reads:

db.getMongo().setReadPref("secondary")

Read the replicated data:

db.getSiblingDB("collegeDB").replicationDemo.find()

The document should appear after replication catches up. If port 27018 is the
PRIMARY after an election, use another member currently reported as SECONDARY.

------------------------------------------------------------
3. READ PREFERENCE: READ ROUTING AND PERFORMANCE
------------------------------------------------------------

Read preference controls which eligible replica-set members may serve reads.
It does not, by itself, guarantee the freshest data.

Run these in a mongosh connection to the replica set. A replica-set-aware
connection is recommended:

mongosh "mongodb://localhost:27017,localhost:27018,localhost:27019/?replicaSet=rs0"

A. Read from the primary (default):

db.getMongo().setReadPref("primary")
db.getSiblingDB("collegeDB").replicationDemo.find()

B. Prefer a secondary:

db.getMongo().setReadPref("secondaryPreferred")
db.getSiblingDB("collegeDB").replicationDemo.find()

C. Read only from secondaries:

db.getMongo().setReadPref("secondary")
db.getSiblingDB("collegeDB").replicationDemo.find()

This may fail if no eligible secondary is available.

D. Prefer a low-latency eligible member:

db.getMongo().setReadPref("nearest")
db.getSiblingDB("collegeDB").replicationDemo.find()

E. Prefer primary, but allow secondary fallback if primary is unavailable:

db.getMongo().setReadPref("primaryPreferred")
db.getSiblingDB("collegeDB").replicationDemo.find()

Summary:
- primary: primary only
- primaryPreferred: primary first, secondary fallback
- secondary: secondary only
- secondaryPreferred: secondary first, primary fallback
- nearest: eligible member with suitably low network latency

For stronger consistency requirements, also consider read concern and write
concern. Read preference alone does not guarantee reading the latest write.

------------------------------------------------------------
4. WRITE CONCERN: ACKNOWLEDGMENT AND DURABILITY
------------------------------------------------------------

Write concern specifies the acknowledgment required before a write is reported
as successful.

A. Acknowledge from the primary (w: 1):

db.getSiblingDB("collegeDB").replicationDemo.insertOne(
  { student: "Priya", marks: 95 },
  { writeConcern: { w: 1 } }
)

B. Request majority acknowledgment:

db.getSiblingDB("collegeDB").replicationDemo.insertOne(
  { student: "Rahul", marks: 88 },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
)

C. Request majority acknowledgment and journal acknowledgment:

db.getSiblingDB("collegeDB").replicationDemo.insertOne(
  { student: "Neha", marks: 91 },
  { writeConcern: { w: "majority", j: true, wtimeout: 5000 } }
)

D. Verify the documents:

db.getSiblingDB("collegeDB").replicationDemo.find()

Notes:
- w: 1 asks for acknowledgment from the primary.
- w: "majority" asks for acknowledgment from a majority of voting members.
  In a three-voting-member set, the majority is two members.
- j: true requests journal acknowledgment, subject to deployment/storage
  configuration.
- wtimeout limits how long MongoDB waits for the requested acknowledgment.
  A timeout does not necessarily mean the write was rolled back; the write may
  already have been applied.
- Stronger acknowledgment requirements may increase latency.

------------------------------------------------------------
5. ELECTIONS: HANDLING PRIMARY FAILURE
------------------------------------------------------------

An election chooses a new primary when the current primary becomes unavailable
or steps down. A voting majority and an eligible candidate are required.

A. Identify the current primary:

db.adminCommand({ hello: 1 })
rs.status().members.map(m => ({
  name: m.name,
  state: m.stateStr
}))

B. Simulate a primary failure safely:
1. Note which port is currently PRIMARY.
2. Go to the Terminal tab running that specific mongod process.
3. Press Control+C to stop that process gracefully.
4. Wait several seconds.
5. From a remaining member, connect to the replica set:

mongosh "mongodb://localhost:27018,localhost:27019/?replicaSet=rs0"

If the old primary was on a different port, use the two remaining ports in
the connection string.

C. Check the new roles:

rs.status().members.map(m => ({
  name: m.name,
  state: m.stateStr
}))

Expected: if two voting members remain available and an eligible candidate
exists, one remaining member should be elected PRIMARY and the other remain
SECONDARY. Elections may take several seconds.

D. Test a write after the election:

db.getSiblingDB("collegeDB").replicationDemo.insertOne(
  { student: "Vikas", marks: 86 },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
)

E. Restart the stopped server:
In the original terminal tab, rerun the matching command with the same port
and dbpath. Example for port 27017:

mongod --replSet rs0 --port 27017 --dbpath ~/mongo-replica/data1 --bind_ip localhost

Then check rs.status() again. The restarted member will generally rejoin as a
SECONDARY after it catches up, though roles can change after future elections.

IMPORTANT: Since all members run on one Mac, shutting down the Mac affects all
members. This exercise demonstrates election behavior, not machine-level
disaster recovery.

------------------------------------------------------------

db.getSiblingDB("collegeDB").replicationDemo.find()
db.getSiblingDB("collegeDB").replicationDemo.countDocuments({})

------------------------------------------------------------
7. TROUBLESHOOTING
------------------------------------------------------------

- NoReplicationEnabled:
  The mongod process was started without --replSet rs0. Stop that process
  gracefully and restart it with the correct server command.

- Address already in use:
  A process is already listening on that port. Check with:
  lsof -nP -iTCP:27017 -iTCP:27018 -iTCP:27019 -sTCP:LISTEN

- No primary available:
  Confirm all intended mongod processes are running and check rs.status().
  A voting majority must be available for a primary election.

- Secondary read fails:
  Set read preference to secondary/secondaryPreferred as appropriate and
  confirm the target member's state is SECONDARY.

- Write concern timeout:
  Check member health and connectivity. A timeout does not prove that the write
  was rolled back.

- setName absent from hello output:
  If replication is enabled but not yet configured, hello may show:
  info: "Does not have a valid replica set config"
  After rs.initiate(), check hello again.

Security note: This local learning setup has access control disabled unless
configured separately. Bind to localhost only and do not expose these ports
to an untrusted network.
